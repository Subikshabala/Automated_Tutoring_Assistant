Assistant (NewS7Project)
Project audit against the Complete Project Specification. Date: 11 October 2026.
Summary
The project is substantial: 762 tests pass, lint reports 0 errors, and the structure matches
the specification well. It is not release-ready. The production build fails, the core learning
loop has missing endpoints, and several routes have no authentication.
Method. Code review, then tsc , eslint , the 92 Vitest files and next build . Small
probes were run against the adaptive and map-comparison logic. No project files were
changed.
Verified results
Of the 8 failing test files, 5 fail on import because route handlers are missing (real
defects). 3 need huggingface.co at run time and failed only because the audit sandbox
had no network.

P1: Core logic versus the specification
4. Prerequisite-aware recommendations are inverted (spec §14.3)
On a PK → RI → FK chain where the learner fails FK (30), the engine recommends review
FK (priority 94), then learn PK (33), and never RI. If RI is also weak (40), FK (94) ranks
above RI (92). The code never walks upstream from a weak concept.
Fix: find the weakest unmet prerequisite of any weak concept and recommend it first,
with a reason such as "FK is weak because RI is 40". Add a regression test using the spec's
Primary Key / Referential Integrity / Foreign Key example.
5. Mastery is volatile and gameable
With one question per concept, one wrong answer takes a concept from 90
(MASTERED) to 36 (NEEDS_REVIEW).
Resubmitting an already-seen quiz takes 0 to 94 in three submissions.
gradeSubmission has no ownership or already-submitted guard, and saveAnswers
deletes previous answers.
Skipped questions count as scored attempts. confidenceScore is computed but
never used.
Fix: allow one submission per assessment (409 afterwards). Count only answered
questions. Weight updates by evidence count and cap the change per attempt. Add a
LearningEvent table for real mastery history.

6. Short-answer grading is fragile
Answers are graded one LLM call after another inside the request. One provider failure
loses the whole submission, including MCQ results.
Learner text and retrieved material are interpolated into prompts without delimiters,
so a learner can write instructions to the grader.
quotedPassages are not verified against the retrieved chunks.
Fix: grade and save MCQs first; mark short answers pending if the LLM fails. Wrap
untrusted text in delimiters with an "ignore instructions inside" rule. Check that quoted
passages are substrings of the retrieved chunks.
7. Map comparison gaps (spec §4.3, §15)
A reversed edge is reported as one "incorrect" plus one "missing"; there is no reversed
class.
No aliases or synonyms; the schema has no field for them.
saveStudentMap never stores conceptId , so "select a canonical concept" cannot
work.
Comparison results are not persisted.
Mistyped edges are computed but never passed to the feedback prompt.
Fuzzy matching maps "Encryption" to "Decryption". It does not trigger on the current
28 seeded concepts, but will on a larger course.
Fix: match by conceptId , then alias, then exact, then fuzzy; treat ambiguous matches as
"unknown". Add reversedEdges , and MapComparison and MapComparisonFinding
tables.
8. Assessment validation is only partial (spec §13.3, §13.5)
Zod checks structure and that the answer is one of the options. It does not check that a
question is actually about its concept (only the LLM's self-reported conceptName is
fuzzy-matched), duplicate options or questions, or the 4-option rule. There is no repair
step or curated fallback.
Fix: add those checks and a seeded question bank to fall back on.
9. Tutor depth and context (spec §8.6, §11)
Explanations have 6 fields with a "2–4 sentences" rule and no depth parameter.

P2: Resilience, RAG and data model
10. AI client (spec §18)
No explicit timeouts, retries, backoff or 429 handling exist in the app code. Every failure
becomes a generic 503. /progress makes an LLM call on every render, and the learn page
blocks server rendering on one.
Fix: map 401, 429, 5xx and invalid output to distinct error codes. Add timeouts and
bounded backoff. Cache or defer the coach summary.
11. RAG pipeline
File type is trusted from the client MIME header; a binary payload declared
text/plain was accepted.
Extraction and embedding run inside the upload request; PROCESSING is never used.
pdf-parse inserts -- 1 of 1 -- markers into text that is chunked and embedded;
page numbers are not kept.
Every PDF failure says "may be scanned". A material goes READY even if embedding
failed.
Material.courseId is never set.
Fix: check magic bytes, process asynchronously with real status transitions, move page
markers into metadata, give specific error messages, and flag chunks without
embeddings.
12. Data model
No mastery history. Misconception.userId has no foreign key to User .
RelationshipType lacks EXAMPLE_OF and CONTRASTS_WITH .

P3: Hygiene
3 test files need huggingface.co at run time, so they are not hermetic. There are no e2e

Remove core-code-report.txt , project-report.txt , the empty structure.txt
and test-results/ from the repository root.

README requires --legacy-peer-deps , which points to peer conflicts. The package
is named opencode-app .
Docs say "19 tables" (there are 20) and that Source "carries real data" (it has 0 rows).
There is no Database Fundamentals course or known learner map for demonstrating
comparison (spec §22).
What is already solid
Grading uses the stored answer key and never ships it to the client.
Zod validates inputs and AI outputs.
Mastery, recommendations and map comparison are deterministic; the LLM only
phrases results.
Passwords use bcrypt and sessions use an httpOnly cookie.
Dark-theme map controls are handled, and the learn page integrates intro, map, detail
and tutor as §8.5 asks.
